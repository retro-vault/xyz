# XCC C11 Coverage Report

This report describes the observed state of C11 support in `xcc` as studied
from the current source tree and from local probe compilations on 2026-05-26.

This document is intentionally stricter than the older status docs.

For this report, a feature is only considered truly complete when it is:

- parsed correctly
- semantically modeled correctly
- lowered correctly
- code-generated correctly
- backed by working runtime support when needed
- tested in a way that checks behavior, not only assembly shape

## Status Legend

- `Solid`: implemented in source and covered reasonably by current tests
- `Partial`: accepted by the compiler, but semantics, runtime, or testing are incomplete
- `Broken`: source inspection or probe compilation shows incorrect behavior
- `Untested`: present in code or docs, but not convincingly validated

## What Looks Solid Today

These areas look meaningfully implemented and are exercised by the current
core regression suite:

- basic scalar types and pointer types
- ordinary expressions and assignments
- `if`, `while`, `do`, `for`
- function declarations, definitions, and normal calls
- arrays, struct field access, pointer dereference
- typedef-driven parsing
- `_Static_assert`
- `_Generic`
- compound literals
- designated initializers
- bit-fields
- VLAs at the current codegen level
- anonymous structs/unions
- built-in preprocessor support
- inline `__asm__`
- basic IR optimization and peephole cleanup

That said, "solid" here means "looks good inside the current project scope".
It does not mean "already validated against a broad external C11 corpus".

## Features That Are Present But Still Partial

### Floating-point support

Status: `Partial`

The compiler parses and lowers float operations, and the backend emits calls
to helpers such as `__fsadd`, `__fssub`, `__fsmul`, `__fsdiv`, `__fitosf`,
and `__fstoi`.

Problem:

- the runtime helpers in `lib/runtime.s` are stubs that return zero

Meaning:

- the frontend and backend path exists
- real floating-point semantics do not yet exist out of the box

### `long long` arithmetic

Status: `Partial`

`long long` types exist, and some wide-value movement is present.

Problem:

- `__mulll`, `__divll`, and `__modll` are empty stubs in `lib/runtime.s`

Meaning:

- support is not end-to-end complete

### Complex numbers

Status: `Partial`

The parser, type system, and IR know about `_Complex`, and there is test
coverage for basic complex arithmetic.

Problems:

- runtime helpers like `cabsf`, `cargf`, `__fssqrt`, and `__fsatan2` are still stubs
- complex division is not meaningfully implemented in the lowering path

Meaning:

- the feature exists in structure
- the feature is not complete in runtime semantics

### `_Thread_local`

Status: `Partial`

The compiler emits TLS-aware addressing and creates TLS template data.

Problem:

- runtime hook `__tls_base` is a stub that returns null unless the OS replaces it

Meaning:

- the compiler side is conditional on external runtime integration

### `_Atomic`

Status: `Partial`

There is real work here:

- `stdatomic.h` exists
- runtime helpers exist for 1-byte and 2-byte atomic operations
- the design uses `DI`/`EI`

Problems:

- memory orders are ignored
- the support is not truly general across larger object sizes
- `_Atomic long` currently compiles through 16-bit helper paths, which is not
  correct for a 32-bit `long` on this target

Meaning:

- `_Atomic` is only partially complete today

### `volatile` and `restrict`

Status: `Partial`

These qualifiers are parsed and stored in type objects.

Problems:

- `volatile` does not appear to drive codegen or optimization barriers
- `restrict` does not appear to influence optimization or alias reasoning

Meaning:

- they are currently more syntactic than semantic

## Features That Are Currently Broken

These are not just incomplete. They are observably wrong from source reading
and probe compilations.

### Named labels and `goto`

Status: `Broken`

Probe result:

- a normal label statement like `done:` causes a parse error

Meaning:

- `goto` and named labels are not actually usable as ordinary C control flow

### `switch` / `case` / `default`

Status: `Broken`

Probe result:

- a simple `switch (x) { case 0: ... case 1: ... default: ... }` compiles to
  labeled return blocks with no comparisons against `x`

Meaning:

- the current lowering does not implement real switch dispatch
- this is much more serious than "no jump tables yet"

### Enumerator constant expressions

Status: `Broken`

Probe result:

- `enum { A = 1 + 2 };` does not behave like a proper constant-expression
  enumerator definition

Meaning:

- enumerator initializers currently behave correctly only in a narrower subset
  than full C11 requires

### `static` local variables

Status: `Broken`

Probe result:

- `static int x = 3;` inside a function is emitted as an ordinary stack local

Meaning:

- storage duration and persistence are wrong

### File-scope `static` variables

Status: `Broken`

Probe result:

- file-scope `static` variables are still emitted as global exported symbols

Meaning:

- internal linkage is not honored for global variables

### `extern` declarations

Status: `Broken`

Probe result:

- `extern int x;` still causes storage allocation in output

Meaning:

- declaration-only extern references are being treated like definitions

### Complex division

Status: `Broken`

The current complex arithmetic helper handles add, subtract, and multiply.
Division falls through without a meaningful implementation.

Meaning:

- complex support is not complete even before runtime concerns

## Areas Where The Docs Overstate Reality

These are the biggest examples where the current tree is more honest than the
existing docs:

- `switch` is described as implemented, but the lowering is not correct
- `goto` and labels are described as implemented, but ordinary named labels fail
- float support is listed as implemented, but the shipped runtime helpers are stubs
- `long long` arithmetic is listed as implemented, but core runtime helpers are stubs
- `_Atomic` looks broader on paper than it is in real object-size coverage
- the current test suite proves compile-time assembly shape, not runtime behavior

## What Is Still Missing For Credible "Complete C11" Coverage

If the goal is "credible C11 coverage for this project", the next work should
be grouped by level.

### 1. Correctness blockers

These should be fixed first:

- named labels and `goto`
- real `switch` lowering
- enum constant-expression evaluation
- correct `static` and `extern` variable semantics
- correct complex division handling

### 2. Runtime completeness

These features should either work or be explicitly downgraded in docs:

- soft-float helpers
- `long long` mul/div/mod helpers
- complex math helper functions
- TLS runtime integration expectations
- atomics for 32-bit objects

### 3. Semantic completeness

These need more than parsing:

- `volatile` semantics
- `restrict` semantics
- `_Atomic` memory-order story

### 4. Validation completeness

The test strategy must grow from "assembly looks right" to "program behaves
right".

Needed test layers:

- negative compile tests
- runtime or emulator-backed execution tests
- `-O1` and `-O2` behavioral tests
- library header tests
- targeted tests for atomics, TLS, float, complex, storage duration, and switch

## Practical Conclusion

`xcc` already supports a useful and interesting subset of C11.

But today it is more accurate to say:

"The compiler has broad front-end coverage and a real Z80 pipeline, but a
group of advanced or storage-related features are still partial or incorrect,
especially where runtime support or control-flow lowering is involved."

That is still a good place to be.

It just is not the same as complete C11 coverage yet.
